# 工具結果不是回合邊界 —— 在已對齊的範圍內繼續串接

**規則**：工具結果回傳後，**在已對齊的範圍內繼續串接下一個工具**。
除非下列 3 個條件之一成立，否則**不要**自動停下來「等使用者確認」：

1. **策略性的模糊決策** —— 範圍不清 / 多個有效方法但無客觀決勝標準 / 使用者意圖不明 /
   需要決定新方向（用 `AskUserQuestion`）
2. **前方有不可逆 / 破壞性動作** —— `git push` / `git reset --hard` / 刪 production code /
   改共用基礎設施 / 改 CI/CD / 發外部訊息（PR comment / email）
3. **使用者明確喊停** —— 「停」/「等一下」/「先確認」/「先檢查」

## 真實案例（來源專案，2026-05）

在單一個 phase 的設置過程中，使用者明確指出了 **4 次**不必要的停頓：

1. `Glob` 回傳了 plan + checklist 的路徑後 → AI 停下來，而不是立刻讀這兩個檔
2. 標記任務完成後 → AI 停下來，而不是立刻批次處理下一批
3. 讀完一個設定檔後 → AI 停下來，而不是平行讀剩下 4 個檔案
4. 寫完 plan.md 後 → AI 停下來，而不是立刻寫同層的 checklist + progress

每次停頓 = 使用者 ~30-60 秒 + 重新進入狀況的認知成本 + 挫折感。
累積損失約 5-10 分鐘 + 多次人工矯正。

## 根因：三條本身有效的規則被**過度套用**到單一工具執行層

| 規則 | 原意 | 被誤讀成 |
|------|------|---------|
| 「行動前先問」 | 策略決策 | 每次 Write/Edit/Read 都問 |
| 「破壞性操作前必問」 | git push / 刪 prod | 本機檔案 Write |
| 「不清楚就停下」 | 真正模糊的時刻 | 工具結果回傳 |

**系統層面的混淆因素**（也記下來以免再被誤導）：

- 每個工具結果都帶著 `<system-reminder>` 的提示文字 —— 那是**提示**，不是停止訊號
- 「行動前考量影響半徑」是給**不可逆操作**的，不是給 Write/Edit 的

## 怎麼做（= 什麼時候該繼續串接）

1. **Phase 設置 = 1 個回合的交付物** —— Plan + Checklist + progress Day 0 全部屬於同一個回合。
   不要拆成 3 個回合「讓使用者檢視」—— **plan + checklist 本身就是檢視用的產物**
2. **批次平行工具呼叫** —— 接下來 3-5 個工具彼此無依賴時（平行讀 5 個檔、平行寫 3 個新檔），
   在同一個區塊裡一次發出
3. **有依賴的工具直接串** —— Read → Edit → Read → Write 在對齊的範圍內是**一個**邏輯動作，不是 4 個回合
4. **把工具結果當成「繼續」訊號**，不是「使用者可能想看一下」訊號。
   使用者是透過讀最終摘要或實際的檔案來檢視的，不是逐個檢查工具結果
5. **只在策略邊界確認** —— `AskUserQuestion` 用於：4 個有效策略選哪個 / N 個優先項先做哪個 /
   啟動一個多 phase 的大工程前。**不用於**：「我該寫下一個檔案嗎」/「plan 看起來 OK 嗎」

## 什麼時候停**是**對的

- 範圍不清 → 用 `AskUserQuestion` 先對齊策略
- 破壞性操作前
- Day-0 drift 發現使範圍變動 > 20% → 回頭跟使用者確認
- 使用者明確喊停
- 2-3 個有效方案但沒有客觀決勝標準 → 讓使用者挑

## 「不清楚就停下」的正確觸發

✅ 觸發：「我不確定使用者要 A 還是 B」/「plan 說 X 但 repo 狀態顯示 Y」/「命名這個方法很困惑，因為抽象不清楚」

❌ 不觸發：「我剛寫完 plan，該寫 checklist 了嗎」/「我剛讀完一個檔，該讀下一個嗎」/「工具回傳 OK，然後呢」
