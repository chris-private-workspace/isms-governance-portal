# 重啟本機開發 Stack

> ⚠️ **這個 command 含破壞性操作**（殺進程 / 清建置快取）。**先跑 `/preflight`** 了解現況。
> 判準與陷阱：`docs/rules-on-demand/local-runtime-ops.md`（**先讀**）。

---

## 兩條範圍鐵律（方向相反，都要守）

1. **「重啟服務」預設指整個 stack**，不是只重啟你剛改過的那個。
   只重啟後端會留下前端拿著 stale 狀態 —— 症狀看起來像資料遺失，其實不是。
2. **但「重啟」就只是重啟。**
   ❌ 不要順手跑測試 · ❌ 不要順手修 bug · ❌ 不要順手改設定 · ❌ 不要順手開 plan。
   使用者要的是一個能用的環境，**不是要你趁機做別的事**（那些都需要自己的 pre-doc，PROCESS R1）。

---

## 順序

服務清單、啟動指令、port 見 **`CLAUDE.md` §Services / Ports**。
**依相依順序**（資料層 → 後端 → 前端），**每步驗 ready 才走下一步**。

### 每個服務的通用步驟

1. **先確認現況**（`/preflight`）—— 已經健康的服務不需要重啟
2. **停舊的**：
   - 以**佔用目標 port 的 PID** 為準，不要用名稱模糊比對
   - ⚠️ 一個服務可能有**兩個進程**（launcher + 子進程）—— 那是同一個服務
   - ⚠️ parent 鏈 root 是使用者終端的 = **他自己開的，留著**
   - ⚠️ 撞到不認得的相關進程 → **停下來問**，可能是另一個 session 的
3. **起新的**
4. **驗 ready**：**不要只等「Ready」字樣** —— 實際打一次健康端點，
   隔幾秒再確認 port 仍在 LISTEN（損壞的情況會 ready 之後立刻崩）

### 前端 / 有建置快取的服務

**清快取再起**。強殺或並行跑會留下損壞的建置快取，症狀不會讓你聯想到快取
（連根路徑 404、本機建置紅但 CI 綠）。快取會自動重建，**刪除是安全的**。

---

## 起完必驗

- [ ] 每個服務的健康端點回 2xx（**端點為準，不看容器旗標**）
- [ ] 主路徑打得開（不是只有 API 通）
- [ ] 回報一張表：`服務 | port | 狀態 | 備註`

**不要**在這裡順便宣稱功能可用 —— 那要 drive-through（`.claude/rules/verification-discipline.md`）。
