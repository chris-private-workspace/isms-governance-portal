# CH-045: 審計負責揪出漂移，BACKLOG 負責承接它 —— 兩份指令原本各講一半

**Date**: 2026-08-20
**Phase**: 無 —— 獨立 CH
**Scope**: 治理流程指令（`.claude/skills/status-audit/` · `.claude/commands/status-audit.md`）
**Components**: —
**PR**: PR-pending

---

## Problem

`/status-audit` 的兩份現行文字對「發現漂移之後要做什麼」給出**相反的指令**：

| 來源 | 原文 | 要求 |
|---|---|---|
| `.claude/skills/status-audit/SKILL.md:44-45` | 「**發現的漂移要回頭修來源**，不是只寫進快照。只寫快照 = 下次再發現一次。」 | **修** |
| `.claude/commands/status-audit.md:93` | 「**不可以順手修漂移**（除非使用者要求）—— 審計負責揪出來，修是另一件事」 | **不修** |

兩份都是現行文字，沒有一份說「以那邊為準」⇒ 執行者照**先讀到的那一份**做。
**這條是跑審計 #9 時撞到的**（`STATUS_AUDIT.md` §2.7-#9 `AD-59`），不是靜態複查猜的。

量化後果：#9 產出 **10 條漂移**（`AD-50`~`AD-59`），進到 `BACKLOG.md` 的是
**1 個指標區塊、0 列**可排序條目（`git show 93151a1 -- .../BACKLOG.md`：12 行全在檔頭 blockquote）。
#7/#8 的 23 條至今處置 4 條、**19 條未處置**，同樣只活在快照裡。

---

## Root Cause

⭐ **不是「兩份文字沒同步」。是兩份各自只講對了一半，而那一半剛好互斥。**

- command 那半是對的：**修掉的那一行往往正是那條發現的實據**。
  審計 #9 的 `AD-51` 就是活例 —— 矛盾的兩半都在 `BACKLOG.md` 裡，
  修掉任一半，那條發現就沒有證據了。當場修還會改掉下一次審計的基準。
- skill 那半也是對的：**只寫快照 = 下次再發現一次**。
  實測 2026-08-20：`BACKLOG.md` §Open 表裡 `AD-{數字}` 形式的列數是 **0**
  （`grep -E '^\|\s*AD-[0-9]+\s*\|' docs/01-planning/BACKLOG.md` 零命中）——
  審計 #7 ~ #9 的 **33 條**發現（18 + 5 + 10）沒有一條**以自己的 ID** 進到那張表。
  ⭐ 而審計 **#1 做過這件事** —— `BACKLOG.md:536` 記著
  「`AD-4` 揭露的 M0 缺口已登記為 `AD-SecDoDAutomation-1`（本表）」，
  該列今天仍在。**⇒ 這不是從未有過的做法，是退化掉的做法。**

  ⛔ **這句話我收緊了兩次，兩次都是同一個錯（拿代理指標回答要讀內容的問題）**：
  (1) 第一版拿 `AD-33 → AD-49 → AD-55` 當證據 —— 推翻：其載體
  `AD-RegisterUpkeep-1` **就在表裡**（`BACKLOG.md:376` P1）而它仍重複三次
  ⇒ 那是**排序**問題不是**承接**問題；(2) 第二版寫「沒有一條進得了那張表」——
  仍超出量到的東西，零個 `AD-{數字}` 列證明不了零個被追蹤。
  **兩個界線都寫進指令本身**，否則下一個人會拿「進了表還是沒被修」
  或「其實有 AD 在追」否定整條規矩。

真正缺的是**中間那一步**：漂移從「被發現」到「被修」之間沒有承接的地方。
`STATUS_AUDIT.md` §2.7 是**點時間快照**（`SKILL.md:52`：§2 覆寫、§3 精簡歸檔），
結構上不是待辦清單；而 §Open Carryover ADs 是待辦清單，
審計卻只往它的**檔頭 blockquote** 寫指標，**從不往表裡加列**。

⛔ 這個洞早被機械層寫在紙上，只是沒人讀成一條缺陷 ——
`check_backlog_counts.py:21-23` 自述其射程邊界：
「檢查的是宣告與表格是否相符…**一個從未被寫進表的 AD 在這裡是不可見的，
就像它對其他每一樣東西一樣。**」

---

## Solution

**裁決（使用者 2026-08-20）**：審計**不修來源**，但**必須在 `BACKLOG.md` 產生可排序的條目**。

| 檔案 | 類型 | 說明 |
|------|------|------|
| `.claude/skills/status-audit/SKILL.md:44-45` | 修改 | 硬規矩 3 由「要回頭修來源」改寫為「要落進 `BACKLOG.md` 成為可排序條目」，並**同時**釘死兩個否定：不當場修（實據會被銷毀）、不只寫快照（下次再發現一次）。程序指回 command §收尾 2 |
| `.claude/commands/status-audit.md:85` | 修改 | §收尾第 2 步由「加一行指標」擴為**兩樣東西**：一行指標 + **每條漂移在 §Open 有一列**。⭐ 分兩支：**已有具名 AD 在追** → 在那一列備註補「審計 #{N} 第 M 次」；**沒有** → 新增一列。並標明加列要同步改 `BACKLOG.md` 檔頭計數（`check_backlog_counts.py` 會比對兩邊） |
| `.claude/commands/status-audit.md:93` | 修改 | §不可以做的事第 2 條保留「不可以順手修」，補上**為什麼**（實據）與**邊界**（「不修」≠「不留待辦」），並指回 §收尾 2 |

### 關鍵設計細節（拿掉就會壞）

- ⭐ **兩份都要改，而且改的是不同的半邊。** 只改 skill（刪掉「要修來源」）會讓
  「發現之後做什麼」變成無人負責；只改 command 會留下 skill 那句相反的話。
  這條 AD 的形狀是**互斥**，不是**其中一份過時**。
- ⭐ **落點選 §Open Carryover ADs，不新開一個 §Open Audit Drifts。** 新開一節等於
  再造一份要同步的清單 —— `SKILL.md` 硬規矩 2 禁止的正是這個。已驗證相容：
  `check_backlog_counts.py:82` 的 `AD_ROW_RE = ^\|\s*(AD-[A-Za-z0-9._-]+)\s*\|`
  對 `AD-50` 這種數字 ID 匹配成功 ⇒ detector 無須改動。
  ⚠️ 代價是數字 ID 與具名 ID（`AD-MockDropsInterpolation-1`）混在同一欄 —— 刻意的：
  同一條發現在快照 / BACKLOG / commit message 用同一個 ID，可追溯性優先於欄位外觀。
- ⭐ **「先查有沒有現成的 AD」那一支不能省。** 少了它，這條規矩會在每次審計
  替**同一個**漂移生一列新的（`AD-33` / `AD-49` / `AD-55` 會變成三列），
  而重複列正是 `SKILL.md` 硬規矩 2 要防的東西。⇒ 規矩本身會製造它要解的問題。
- ⛔ **加列必須同步改 `BACKLOG.md` 檔頭的計數宣告**，否則 `check_backlog_counts.py` 轉紅。
  這一句寫進 command，因為忘記它的後果是下一次審計自己把 gate 弄紅。

### ⛔ 射程限制（明寫以免被當成全覆蓋）

1. **這是文字層的修正，沒有機械守衛。** 沒有任何 detector 會檢查
   「§2.7 的漂移條數 == 本次新增的 §Open 列數」。要有守衛得另開一片。
2. **審計 #9 的 `AD-50` ~ `AD-59` 未回填。** 本片只改規則，規則自審計 #10 起生效。
   回填是使用者的排序權（§Step 0.0），且 `AD-51` 的處置需要單獨判斷 ——
   它的實據就是 `BACKLOG.md` 裡那一行，回填時不可順手把它修掉。
3. ⛔ **本片不解「進了表卻沒被排到」。** `AD-RegisterUpkeep-1` 是現成反例：
   在 §Open 表裡（P1）而它指的漂移仍重複三次。本片只保證漂移**進得了隊伍**，
   隊伍怎麼排是使用者的權（§Step 0.0 的節流閘）。
