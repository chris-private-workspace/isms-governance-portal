## Day 1 — 能跑起來 ⭐

**今天的成功判準**：**在本機跑起來並看到它運作**。不是讀完文件。

### 環境

- [ ] Repo clone + 依賴安裝
- [ ] `.env` 從 `.env.example` 建立並填好（**問 buddy 拿需要的憑證**）
- [ ] 服務起得來
- [ ] 完整 gate 跑過一次：
  ```bash
  <lint 指令>
  <test 指令>
  python scripts/lint/run_all.py
  ```
- [ ] **實際開起來用一次** —— 走一次主要功能（這是你的第一次 drive-through）

### 讀（只有這兩份是今天必讀）

- [ ] `CLAUDE.md` §Core Vision —— **這個專案在做什麼、為什麼**
- [ ] `docs/INFORMATION-FLOW.md` —— **開發時讀什麼、產生什麼、更新什麼**

### 卡住的話

記下來，明天問 buddy。**不要自己卡超過 30 分鐘** —— 環境問題通常是別人已經知道的坑。

> 卡住的點請回報給 buddy，**這是 setup 文件的 bug**，要修的是文件不是你。

## Day 2-3 — 理解結構

### 讀

- [ ] `docs/01-planning/README.md` + **2-3 份**最相關的核心設計文件（不是全部）
- [ ] `.claude/rules/` 4 條 always-loaded
- [ ] `MEMORY.md` §Principles —— 跨專案的行為教訓
- [ ] ⭐ **挑 3 個最近的 CHANGE record 讀**
  （`docs/03-implementation/changes/`，選編號最大的三個）

> 最後這一項比讀設計文件更快理解**這個團隊怎麼想事情** ——
> 設計文件說「應該長怎樣」，CHANGE record 說「實際怎麼決定的」。

### 做

- [ ] 挑一個**小改動**（buddy 指定），走完完整流程：
  - 用 `/fix` 或 `/change`
  - 產出對應的 change record
  - 開 PR 並走完 review
- [ ] 目標**不是產出**，是**走通流程**

## 給 Buddy 的清單

- [ ] Day 1 前把憑證 / 存取權準備好（**這是最常見的 Day 1 阻塞**）
- [ ] Day 1 一起把環境跑起來（不要讓他自己摸一天）
- [ ] 指定第一個小任務（**小到一天內能走完流程**）
- [ ] Day 3 review 他的第一個 PR —— 這次 review 要**特別詳細**，它會定調
- [ ] Week 2 結束時問：**setup 文件哪裡不對？** → 當場修掉

## Onboarding 反模式

| 反模式 | 為什麼壞 |
|-------|---------|
| 叫新人先讀完所有文件 | 沒有上下文的閱讀留不下東西 |
| 第一個任務給大的 | 第一個任務的目的是**走通流程**，不是產出 |
| 沒人負責 | 「有問題再問」= 不知道問誰 = 不問 |
| 新人踩的坑沒回頭修文件 | 下一個新人再踩一次 |
