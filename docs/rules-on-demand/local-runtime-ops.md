# 本機服務操作紀律

**Purpose**: 啟動 / 重啟 / 健康檢查本機開發服務時，避免把「慢」誤判成「壞」、
把「別人的進程」誤判成「殘留」、把「範圍」悄悄擴大。

**Category / Scope**: Runtime ops / on-demand rule
**Created**: 2026-08-07
**Last Modified**: 2026-08-07
**Status**: Active

**Trigger（什麼時候 Read）**：重啟服務 / 服務起不來 / 端點連不上 / 要跑會改動狀態的操作
（migration、eval、批次匯入）之前 / 準備殺進程之前。

**Why**：這幾條看起來像瑣事，但每一條都造成過**整輪白費的工** ——
殺掉正在啟動的服務再等一次、殺掉使用者自己開的服務、
或者被叫去「重啟」結果順手改了三個檔。

---

## 1. 「慢」不等於「hang」⭐ 最常犯

冷啟動慢是常態，尤其在剛開機 / 剛跑完建置 / 磁碟仍在被索引的機器上。
**單次探測失敗不構成「掛了」的證據。**

| 判準 | 做法 |
|---|---|
| **先看有沒有在動** | 進程還在？CPU 有沒有跳動？log 有沒有新行？—— 仍在 import / 編譯 = 慢 |
| **timeout 要夠長** | 健康探測 timeout 開太短會把「忙」讀成「死」。忙碌的服務回應本來就慢 |
| **不要提前殺** | 殺掉重啟 = 從頭再等一次冷啟動。**這是負收益的動作** |

> 真實代價：一個 blob 模擬器在重度爭用下要 30-90 秒、一個後端要數分鐘才起得來。
> 每次「等不及就殺」都是把等待時間乘以二。

---

## 2. 健康判準：以端點回應為準，不以容器狀態旗標為準

容器的 health check 有它自己的重試節奏，**warmup 期間顯示 `(unhealthy)` 但端點已經
回 200 是常見的 timing artifact**。

| 訊號 | 權重 |
|---|---|
| 端點回 200 / TCP 通 | ✅ **這才是判準** |
| 容器 `(unhealthy)` 但端點通 | ⚠️ timing artifact，**不阻擋** |
| 端點不通 | ❌ 真的有問題 |

---

## 3. 重啟的範圍紀律：全部重啟，但**只**重啟

兩條都要守，方向相反：

- **「重啟服務」預設指整個 stack**，不是只重啟你剛改過的那個。
  只重啟後端會留下前端拿著 stale 狀態，症狀看起來像資料遺失，其實不是。
- **但「重啟」就只是重啟。** 不要順手跑測試、順手修 bug、順手改設定、順手開 plan。
  使用者叫你重啟就是要一個能用的環境，**不是要你趁機做別的事**。

> 真實代價：一句「重啟服務」被理解成「重啟並順便把它修好」，
> 結果多了一批沒人要求、沒有 pre-doc 的改動（違反 PROCESS R1）。

---

## 4. 殺進程之前，先確認那是誰的

| 陷阱 | 判準 |
|---|---|
| **一個服務兩個進程** | 用 venv / wrapper 啟動時，launcher 會 spawn 一個顯示**系統**直譯器路徑的子進程。**兩個是同一個服務**，不是入侵者 |
| **使用者自己開的** | 追 parent 進程鏈；root 是使用者的終端 = 他自己開的，**留著** |
| **憑猜測清殘留** | 以「佔用目標 port 的那個 PID」為準，不要用名稱模糊比對 |
| **另一個 session 正在開** | 同一個 repo 開了兩個 AI session 時，會互相殺掉對方剛起的服務。撞到陌生進程**先停下來問**，不要當殘留清掉 |

---

## 5. 前端 / 建置快取損壞

強殺開發伺服器或並行跑兩個，會留下損壞的建置快取。特徵是**症狀範圍大於你的假設範圍**：

- 連根路徑都 404 / 500（純 API 層的問題不可能讓根路徑也死）
- **本機 type-check / build 紅但 CI 全綠**（CI 是乾淨 checkout，沒有那份快取）
  —— 這種情況下**紅的那邊才是假的**

處置：停掉殘留進程 → 刪整個建置快取目錄 → 重起。快取會自動重建，刪除是安全的。

> **通則：症狀範圍超出假設範圍時，先重新界定範圍，不要加深假設。**
> 追了三個小時的環境變數 / proxy / DNS，真因是換 port 期間強殺過進程。

---

## 6. 會改動狀態的操作之前，先 preflight

migration / 批次匯入 / 重建索引 / 清資料 之前，先確認相依服務**真的**通。
對著一個半死的環境跑這類操作，得到的錯誤訊息會把你帶去完全錯誤的方向。

任一相依端點不通 → **先向使用者回報，不要自動重啟**（重啟本身也是破壞性動作）。

---

## 7. 備份要經過還原演練，才算備份 ⭐

**一個從來沒有被還原過的備份，不是備份，是一個關於備份的假設。**

本機開發狀態（容器 volume、本地資料庫、物件儲存模擬器的資料、種子資料、
`.env` 的實際值）在「重灌機器 / 換電腦 / 誤刪 volume」時全部會消失。
而這幾件事的共同點是：**你發現備份不能用的那一刻，就是最需要它的那一刻。**

### 兩個腳本必須成對

只寫備份腳本是最常見的半套。備份腳本會跑、會產生檔案、看起來很像有在運作 ——
直到有人要用它。

| 腳本 | 職責 |
|---|---|
| `scripts/backup_local_state.*` | 匯出所有**不可重建**的本機狀態 |
| `scripts/restore_local_state.*` | 從備份還原，**並印出可對數的數字** |

「不可重建」是判準：能用一行指令重跑出來的東西（`node_modules`、建置產物、
快取）不要備份 —— 備份體積會爆，而且會讓真正重要的東西被埋掉。

### 演練的判準：逐項對數，不是「跑完沒報錯」

還原腳本 exit 0 **什麼都不證明**。演練要對的是數字：

- [ ] 資料庫每張關鍵表的**筆數**，還原前後一致
- [ ] 物件儲存的**物件數量 + 總大小**，還原前後一致
- [ ] 應用起得來，且**首頁 / 主流程真的能用**（不是只有 health endpoint 回 200）
- [ ] 設定值還原後**指向的是本機**，不是備份當時那台機器的路徑

> 對數項要**事先列出來、寫進腳本輸出**。事後才想「應該檢查什麼」的話，
> 你會傾向挑那些剛好對得上的東西看。

### 演練節奏

- **建立備份機制的當下**就演練一次 —— 這時候還原失敗的代價是零
- 之後**每次改動備份範圍**（加一個服務、換資料庫版本）要重演一次
- 真的要重灌之前**必演一次**，不要相信上一次的結果

> 真實代價：一份「有在跑」的備份，還原時才發現它備份的是空目錄 ——
> 因為模擬器的資料目錄參數後來改過，而備份腳本沒跟著改。
> 腳本每天都成功執行，每天都在備份一個空的地方，**沒有任何東西會叫**。

---

## 8. 檢查清單（重啟 / 排障時逐項）

- [ ] 先 preflight，知道現況才動手（`/preflight`）
- [ ] 服務起不來 → 先確認是**慢**還是**死**（進程在不在 / CPU / log）
- [ ] 端點通就算健康，不管容器旗標寫什麼
- [ ] 殺進程前確認：是同一服務的子進程嗎？是使用者自己開的嗎？是另一個 session 的嗎？
- [ ] 重啟 = 整個 stack；但**只**重啟，不順手做別的
- [ ] 起完逐個驗端點，不要只看「Ready」字樣
- [ ] 要做破壞性操作（重灌 / 清 volume / 換版本）之前：**備份演練過了嗎？**
