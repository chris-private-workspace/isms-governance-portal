# 多語言 / 術語一致性 — 觸發式規則

**Purpose**: 多語系文案的維護紀律 —— 術語權威、機器守門、以及「第三種譯法」怎麼防。

**Category / Scope**: i18n / on-demand rule
**Created**: 2026-08-07
**Last Modified**: 2026-08-07
**Status**: Active

**Trigger（什麼時候 Read）**：新增 / 修改任何 user-facing 文案 · 加一個新語言 ·
改某個術語的譯法 · 規劃多語言支援 · 翻譯檔報找不到 key。

**Why**：多語系不是「把字串抽出來」這一件事。真正會出問題的是**三件別的事** ——
術語漂移、缺 key 靜靜 fallback、以及硬編碼繞過整套機制。三件都不會自己叫。

---

## 0. 先決定：你現在需要做到哪一層

**規劃階段就要決定，不要等到有第二個語言才想。** 事後補的代價高一個量級 ——
文案已經散落在幾百個元件裡。

| 層 | 做什麼 | 什麼時候夠用 |
|---|---|---|
| **L0 抽字串** | 文案集中在字典檔，元件只放 key | 只有一種語言，但**預期會有第二種** |
| **L1 多語系** | L0 + 多份字典 + 語言切換 + 機器守門 | 真的要出第二種語言 |
| **L2 在地化** | L1 + 日期 / 數字 / 貨幣 / 排序 / 文字方向 | 面向多個地區，不只多個語言 |

⚠️ **L0 的成本遠低於它看起來的樣子，而且它是唯一有時效性的一層。**
只要專案「將來可能要多語言」，L0 就該從第一天做 —— 它不需要任何 i18n 框架，
只需要「文案不寫死在元件裡」這個習慣。

---

## 1. 術語權威表（單一來源）

同一個概念在整個產品裡**只能有一個譯法**。沒有權威表的話，
三個人會產出三種譯法，而且**沒有任何人會發現** ——
因為每個人都只看得到自己那幾頁。

建一份 `<字典目錄>/GLOSSARY.md`，**跟字典檔住在一起**（不要放 `docs/`
—— 改文案的人不會去 `docs/` 翻）。分類建議：

| 類 | 內容 | 例 |
|---|---|---|
| **A 產品專有名詞** | 產品 / 模組 / 功能的正式名稱 | 一律不譯，或一律譯，**不能混** |
| **B 領域術語** | 業務概念 | 「knowledge base → 知識庫」 |
| **C 介面通用詞** | 按鈕 / 狀態 / 動作 | 「Save → 儲存」（不是「保存」） |
| **D 排版慣例** | 中英混排空格 / 標點全半形 / 數字格式 | 「中文與英數之間留一個空格」 |
| **E 已拍板的爭議** | 曾經有分歧、已經定案的 | 記**理由**和**日期**，否則半年後會重新辯論 |

### ⭐ 最重要的一條：不可以靜靜引入第三種譯法

碰到某個詞現有兩種譯法、或者權威表沒有收錄：

> **停下來問，拍板之後補進 E 類。**

**不要**自己挑一個看起來比較好的用下去。那樣做的結果不是「二選一」，
是**變成三種** —— 你的那個加上原有的兩個。而且下一個人會再挑一次。

## 2. 機器守門：缺 key 必須 fail

**這是整份規則裡唯一有強制力的部分。**

多數 i18n 框架在找不到 key 時的預設行為是**回傳 key 名字本身**。
於是頁面上顯示 `settings.profile.title`，沒有錯誤、沒有警告、CI 全綠 ——
**這就是假綠**，而且要等到有人真的切到那個語言才會看到。

必須有一個測試做這三件事：

- [ ] 所有語言的字典檔，**key 集合完全一致**（缺一邊 = 測試紅）
- [ ] 沒有空值 / 沒有殘留的原文佔位
- [ ] 元件裡用到的 key 都存在（能做到的話 —— 需要靜態掃描）

```
# 把這個接進 CI，跟其他 gate 同級
<你的測試指令> <i18n 字典測試>
```

> 「規則要有東西會叫，才算規則」在這裡特別致命 ——
> 因為 i18n 的失效是**視覺上的**，而視覺問題只有切到那個語言的人才看得到，
> 而開發的人通常不切。

---

## 3. 硬編碼是最大的漏洞面

一段寫死在元件裡的文案，**不會出現在任何 i18n 檢查裡** ——
它不在字典檔，所以 key 一致性測試看不到它；它不是缺 key，所以不會 fallback。
它就只是永遠是英文。

- [ ] 元件裡不出現面向使用者的字面字串
- [ ] **包括**：錯誤訊息、`aria-label`、`placeholder`、`title`、
      toast 內容、confirm 對話框、圖表軸標籤、空狀態文案
- [ ] 後端回傳的訊息也算 —— 決定它是「回 key 讓前端翻」還是「後端也做 i18n」，
      **不要兩種混用**

上面那份清單裡，`aria-label` 和空狀態文案是最常漏的兩個。

---

## 4. 翻完要看實際版面

字典檔對齊 ≠ 畫面沒壞。

- 德文平均比英文長 **30%**，日文比中文高（行高不同）
- 按鈕 / 表格標頭 / 側欄是最先爆版的地方
- 中英混排的空格規則不統一時，同一頁會看起來「有點髒」但說不出哪裡怪

**每加一個語言，主要頁面逐頁看一次。** 這件事沒有自動化替代品 ——
跟前端保真度的 drive-through 是同一個道理。

---

## 5. 加一個新語言的順序

1. 複製基準語言的字典檔 → 全部翻譯（**不要留空 key**，寧可先放原文）
2. 跑 key 一致性測試 → 綠
3. 把新語言加進權威表的排版慣例（D 類）—— 標點 / 空格規則各語言不同
4. 逐頁看版面（第 4 節）
5. 切回原語言再看一次 —— **加語言常常會弄壞原本那個**
